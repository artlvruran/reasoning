# GNARL — реализация архитектуры из статьи

Полная реализация архитектуры и MDP-формулировок из статьи
**"Tackling GNARLy Problems: Graph Neural Algorithmic Reasoning Reimagined
through Reinforcement Learning"** (Schutz, Darvariu, Panagiotaki, Lacerda,
Hawes).

Написано на **JAX** (не PyTorch — в песочнице, где это собиралось, диска не
хватило на CUDA-зависимости torch; CPU-сборка JAX самодостаточна и к тому же
соответствует собственному JAX-стеку авторов для NAR-бейзлайнов).

## Структура

```
gnarl/
  model.py            — архитектура Encode → Process → Act (Sec. 4.2, Appendix B):
                         энкодер признаков, MPNN-процессор без рекуррентности
                         между шагами MDP, proto-action актор (Darvariu et al.,
                         2021b) с маскированием действий, критик для PPO.
                         Поддерживает батчинг через jax.vmap (forward_batched).
  utils.py             — генерация графов (ER, BA, Евклидов TSP).
  envs/
    base.py            — базовый класс GNARLEnv / GraphState (M = <S,A,T,R,h>),
                         + pad_state_to/stack_states для батчинга по jax.vmap.
    bfs_dfs.py          — BFS/DFS: Algorithm 1 (transition), Algorithms 9-10
                          (эксперты), Algorithm 8 (проверка корректности DFS).
    bellman_ford.py     — Bellman-Ford: Table 7, Algorithm 3, Algorithm 11.
    mst_prim.py         — MST-Prim: Table 10, Algorithm 4, Algorithm 12.
    tsp.py              — TSP: Definition 1, Table 11, Algorithm 5 (+ Held-Karp
                          как замена решателя Concorde).
    mvc.py              — MVC: Definition 2, Table 12, Algorithm 6 (+ точный
                          ILP через PuLP/CBC как замена решателя из статьи).
  training/
    bc.py               — Behavioural Cloning (Eq. 3): реальные батчи через
                          jax.vmap (группировка по числу вершин + паддинг рёбер).
    ppo.py               — PPO (Eq. 2) с маскированием действий и GAE.

gnarl_experiments.ipynb — ноутбук с экспериментами (архитектура, BFS/DFS/
                          Bellman-Ford/MST-Prim через BC — аналог Table 2;
                          множественные решения через temperature sampling —
                          аналог Figure 2; MVC и TSP через BC+PPO — аналоги
                          Table 3 и Table 4).
```

## Баги, найденные и исправленные в процессе (важно!)

После первого прогона ноутбука вы сообщили о 0%-й точности. Разбор показал
три реальные проблемы:

1. **Пропущенное легальное действие у DFS.** Алгоритм 10 иногда предписывает
   «выбрать саму `psi_1`» (когда все реальные соседи уже посещены, а свой
   `reach`-флаг ещё не выставлен — он ставится отложенно на СЛЕДУЮЩем шаге).
   Маска действий это не допускала → при обучении иногда loss улетал в
   десятки миллионов (несовпадение маски и распределения эксперта).

2. **Потенциальное зависание в проверке корректности DFS.** Если `pred`-массив
   (из-за случайной/недообученной политики) образовывал цикл длиннее одного
   узла, рекурсивный обход зацикливался навечно. Добавлены защитные проверки
   циклов во всех местах, где идёт обход по `pred` (и в BFS, и в DFS).

3. **Главная причина «0% качества»** — при исправлении п.1 self-loop-действие
   было сделано *всегда* легальным в фазе 2, а не только в узком случае,
   который реально описывает Algorithm 10. У BFS (чья экспертная политика,
   Algorithm 9, вообще никогда не рекомендует такое действие) это добавило
   постоянный «отвлекающий» вариант на КАЖДОМ шаге фазы 2 — и модель
   принципиально не могла научиться его подавлять: даже после 1000 эпох
   обучения на фиксированном мини-датасете loss не двигался с места, а
   точность на весь эпизод стабильно была 0%. Сузил условие ровно до
   ситуации, которую описывает Algorithm 10 (`все реальные соседи посещены
   И reach[psi_1] ещё не выставлен`) — это полностью решило проблему.

Также обучение изначально шло через per-example SGD (один граф — один вызов
JIT на пример), что было и медленно (Bellman-Ford — 41 минута на 8 эпох на
Colab GPU из-за overhead диспетчеризации), и недостаточно для сходимости.
`train_bc` переписан на **настоящие векторизованные минибатчи**: примеры
группируются по числу вершин, рёбра паддятся до общей длины внутри группы (c
маской `edge_valid`, которая корректно исключает паддинг из sum- и
max-агрегации), и обрабатываются одним вызовом `jax.vmap`. Численно проверено,
что батчированный forward даёт идентичный результат одиночному. Ускорение —
на порядок; плюс качество обучения выросло за счёт менее шумных градиентов.

### Результаты после исправлений (проверено локально, вне ноутбука)

| Задача | До фиксов | После фиксов |
|---|---|---|
| BFS (полный эпизод, вкл. OOD \|V\|=20) | 0% | ~79–80% |
| DFS (полный эпизод, вкл. OOD \|V\|=20) | 0% | ~67–70% |
| Bellman-Ford (полный эпизод) | 0% | ~55% |
| MST-Prim (полный эпизод) | 0% | ~90% |
| MVC (BC) | работал | точное совпадение с оптимумом |
| TSP (BC) | работал | ~1.1% сверх оптимума |

**Важно про метрику "полный эпизод":** корректность всего эпизода требует
верного выбора *всех* примерно `2(|V|-1)` шагов подряд — ошибки перемножаются
мультипликативно по шагам. Даже 80%-ная точность на шаг даёт лишь
`0.8^14 ≈ 4%` шанс на полностью верный 14-шаговый эпизод. Именно поэтому в
ноутбуке рядом с точностью по эпизоду теперь выводится и **точность по шагу**
(teacher forcing) — это то же самое различие node accuracy / graph accuracy,
которое использует сама статья (Section 2.1). Мы не пытались воспроизвести
абсолютные цифры статьи (там — hyperparameter search по Table 15, полноразмерные
датасеты) — задача была показать, что фреймворк работает и на самом деле
чему-то обучается, а не выдаёт случайный шум.

## Осознанные упрощения (описаны также в коде и в ноутбуке)

- `pred`-указатели закодированы как бинарный edge-признак, а не как
  CLRS-30 pointer-тип.
- TSP-тур строится дозаписью в конец (append), а не через pred-трюк
  "вставка в голову" из Algorithm 5 — эквивалентный по MDP-семантике выбор,
  прямо допускаемый Appendix C.2 статьи.
- В Algorithm 9 (BFS) строка `PhaseTwoPolicy` с условием `reach_j = 1`
  прочитана как `reach_j = 0` (непосещённые соседи) по аналогии с DFS —
  похоже на опечатку/ошибку OCR при выгрузке текста.
- Concorde и специализированный ILP-решатель MVC из статьи заменены на
  Held-Karp (точный DP) и PuLP/CBC соответственно — оба точны для
  используемых в ноутбуке размеров.
- Robust Graph Construction (Section 5.4) не реализован — там пространство
  действий про добавление рёбер, а не выбор узлов, что требует отдельной
  MDP-обвязки; остальные пять сред реализованы полностью.
